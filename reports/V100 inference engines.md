# Stay on llama.cpp, unlock tensor split

The engine that can significantly raise Qwen3.8-27B throughput on the Tellico AC922s is still llama.cpp, rebuilt for these nodes. The cluster runs plain upstream llama.cpp (commit c25030496) with `GGML_CUDA_NCCL=OFF`, so the `--split-mode tensor` code already in its source cannot be used. Both GPUs on each node are therefore reading weights one after the other rather than at the same time. A V100-specific fork, **1115714829/llama.cpp-v100**, targets this exact setup: Qwen3.8-27B with DFlash2 on an IBM AC922 with V100-SXM2-16GB over NVLink and CUDA 12.4. On 2 cards with tensor split it reports **~1,850 tok/s prefill and 63-79 tok/s decode on a real 16K prompt** ([llama.cpp-v100](https://github.com/1115714829/llama.cpp-v100)). That prefill is **3-4x the cluster's 430-650 tok/s**. The decode figure is not directly comparable, but the arithmetic says long-context decode, now ~28-33 tok/s, has the most room to grow. A small Volta kernel patch (**Mitsuasa513/llama.cpp-v100-tuning**) claims a further **+24% decode at 90k and +36-57% prefill** on this model ([Mitsuasa513](https://raw.githubusercontent.com/Mitsuasa513/llama.cpp-v100-tuning/v100-sm70-tuning/README.md)). The one engine with much bigger headline numbers, **1Cat-vLLM**, cannot be installed here. It needs x86_64, glibc ≥ 2.38, CUDA 12.8 and PyTorch 2.10, and CUDA on Power stops at 12.4.1. Upstream vLLM, SGLang, TensorRT-LLM, LMDeploy, ExLlamaV3 and ik_llama.cpp are ruled out for Volta, ppc64le or model-support reasons. My realistic expectation for a tuned llama.cpp is **roughly 1.5-2x on long-context decode, 2-4x on prefill, and 0-30% on short-context decode**. The first gate is getting an NCCL that builds for ppc64le with CUDA 12.4. Nobody has verified that yet.

## The hardware has headroom that the current build leaves idle

Two numbers measured on tellico-compute0 change the picture that the generic sources paint. First, the nodes run **driver 550.54.15 with CUDA 12.4**, even though the OS is RHEL 7.6. NVIDIA's RHEL 7 ppc64le repository stops at CUDA 10.2 and driver 440 ([NVIDIA rhel7/ppc64le repo](https://developer.download.nvidia.com/compute/cuda/repos/rhel7/ppc64le/)), so this cluster is ahead of what a stock RHEL 7 install would allow. The ceiling is still fixed, though. NVIDIA's own staff confirm that CUDA 12.4.1 was the last release for Power and that support was removed in 12.5.0 ([NVIDIA forum](https://forums.developer.nvidia.com/t/missing-cuda-drivers-for-ppc64le-on-rhel9/301323)). CUDA 13 dropped Volta separately ([CUDA Features Archive](https://docs.nvidia.com/cuda/cuda-features-archive/index.html)). **CUDA 12.4 is therefore the permanent toolkit for these nodes.** Any engine that needs a newer one is out, container or not, because a container still runs on the host's kernel driver.

Second, the live layout is unbalanced and serial. At 2×131072 context, GPU0 holds 13,084 MiB and GPU1 holds 16,004 of 16,384 MiB. With llama.cpp's default layer split, each token's weight reads happen on GPU0 and then on GPU1, so the two cards together deliver one card's bandwidth. A back-of-envelope bandwidth model in the platform notes uses 11.8 GB of IQ3_S weights and 900 GB/s per V100 (the bandwidth figure is the standard spec and was not re-sourced). It gives a no-speculation decode ceiling of **~76 tok/s for layer split** and **~110-125 tok/s for ideal two-way tensor parallelism**, after allowing roughly 1.3-2.6 ms per token for allreduce over NVLink. That allreduce latency is an estimate, not a measurement. The measured 72-86 tok/s with DFlash2 implies roughly 41-49 ms per verify step at a mean accepted length of ~3.5. That is about three to four plain decode steps' worth of time, which suggests **raw decode is running at only about a third to a half of the bandwidth ceiling**. The slow parts are kernels and serialisation, not the silicon.

The long-context collapse, from ~86 to ~28-33 tok/s at 64-110k tokens, comes from attention, not from Gated DeltaNet. GDN layers keep a fixed-size state. The full-attention layers read a KV cache that grows with every token, and each verify step reads it for several query positions. Upstream's Volta flash-attention is the weak spot. The 2025 rewrite to PTX mma excluded Volta, which kept the older WMMA kernel ([PR #11583](https://github.com/ggml-org/llama.cpp/pull/11583)). A later GQA speedup was disabled on Volta because it was slower there ([PR #19092](https://github.com/ggml-org/llama.cpp/pull/19092)). Volta FA crashes at head size 256, the head size these Qwen models use, were fixed only on 2026-10-01 ([PR #29803](https://github.com/ggml-org/llama.cpp/pull/29803)). An open analysis issue documents that the Volta branch still falls back to an Ampere config ([issue #28037](https://github.com/ggml-org/llama.cpp/issues/28037)). Two things can help this regime: splitting the KV cache across both GPUs, and better Volta attention kernels. The plan below targets both.

## Ranked options, from deployable to blocked

| Rank | Option | Realistic gain on these nodes | Main blocker | Confidence |
|---|---|---|---|---|
| 1 | Upstream llama.cpp or the 1115714829 V100 fork with `--split-mode tensor` over NCCL | Prefill 2-4x; long-context decode ~1.5-2x; short decode 0-30% | NCCL for ppc64le/CUDA 12.4 (unverified) | Medium-high |
| 2 | Mitsuasa513 Volta FA/MMVQ patch on top of #1 | Further ~+20% decode at depth, +35-55% prefill (single-author claim) | Patch is against a different upstream base; combining it with #1 is untested | Medium |
| 3 | Quant, KV type and draft-length retuning (Q4_0/IQ4_XS vs IQ3_S, f16 KV, lower n-max at depth) | 5-25%, depth-dependent | Only memory, once tensor split balances the cards | Medium |
| 4 | 1Cat-vLLM (V100 vLLM fork) | 2-5x on paper, on 4×32GB x86 | x86_64, glibc 2.38, CUDA 12.8, PyTorch 2.10: none exist for ppc64le | Not deployable |
| 5 | ik_llama.cpp | Likely negative | Turing+ officially; maintainer declines Volta tuning | Low |
| 6 | Upstream vLLM, SGLang, TensorRT-LLM, LMDeploy, ExLlamaV3, qengine | None | sm_75 floors, no ppc64le, no Qwen3.8, or no NVLink | Ruled out |

### Rank 1: tensor split over NVLink, ideally via the V100 fork

Upstream llama.cpp merged `--split-mode tensor` on 2026-04-09. It splits individual tensors across GPUs, recommends NCCL, requires flash attention and an explicit `--ctx-size`, and lists Qwen3.5 27B as working while several other hybrid families are broken ([PR #19378](https://github.com/ggml-org/llama.cpp/pull/19378)). On 2×4090 it lifted decode **1.60x** and *cut* prefill to 0.39-0.64x of layer split. It also has a known VRAM leak from re-created CUDA graphs that can cause OOM as context grows ([PR #19378](https://github.com/ggml-org/llama.cpp/pull/19378)). The leak matters for 131072-token slots. The `--split-mode row` path rejected earlier on this cluster is the old, different code path, and its failure says nothing about tensor split.

The 1115714829 fork has already done the platform work for this exact hardware. It builds with `-DGGML_CUDA_NCCL=ON`, sets `NCCL_P2P_LEVEL=SYS` automatically on ppc64le, recommends `numactl --membind=0,8` because the AC922 exposes GPU memory as NUMA nodes, and ships DFlash2 with `--spec-draft-n-max 7` ([llama.cpp-v100](https://github.com/1115714829/llama.cpp-v100); [v100-1.1.1](https://github.com/1115714829/llama.cpp-v100/releases/tag/v100-1.1.1)). Its 2-card, 131072-context run with a UD-Q4_K_M target and F16 draft used **13.7 GB per card**, prefilled a real 16K prompt at **1,861 tok/s** and decoded at **63.4 tok/s**. A later Q4 draft at 262144 context reached **78.6 tok/s** decode, and the author says Q4 decode improved about 10% since. On 4 cards with real code prompts, it held **102.6 tok/s decode at 131K** ([llama.cpp-v100](https://github.com/1115714829/llama.cpp-v100)). Its prefill gain comes even though tensor split hurts prefill on 4090s, which points to its Volta-specific kernels doing real work. Two cautions apply. First, these are author-measured, on a heavier 4-bit quant, with a DFlash2 acceptance (0.22-0.25) below the cluster's 0.34-0.37, so the comparison runs in both directions. Second, the fork's "synthetic" 162-184 tok/s figures are inflated by easily drafted prompts and should be ignored.

The memory side is favourable. Tensor split spreads weights and KV evenly, so the GPU1 hot spot at 16,004 MiB should fall to roughly the average of today's two cards. That frees room either for a 4-bit target or for unquantised KV. For concurrency, the fork's `-np 2` run on 4 cards gave 120.9 tok/s for a lone request and 84.1 and 103.6 tok/s for two concurrent ones ([llama.cpp-v100](https://github.com/1115714829/llama.cpp-v100)). That is the same shape as the cluster's 72-86 alone versus 52-70 each.

The blocker is NCCL. The cluster's build was configured without it, and no source in the notes confirms an NCCL build for ppc64le with CUDA 12.x. The fork's author evidently has one, since the fork runs on AC922 with CUDA 12.4, so this is very likely solvable. It is still the first thing to establish.

### Rank 2: Volta kernels where upstream has none

Mitsuasa513/llama.cpp-v100-tuning is a +930/-86-line patch on upstream. Its decode FA reads a q8_0 KV cache straight into shared memory with GQA heads sharing tiles. Its prefill tiles fit two blocks per SM, activation quantisation runs once per graph pass, rms_norm and scale are fused, and MMVQ gets a Volta table. On one V100-32GB running Qwen3.8-27B Q4_K_M, the author claims **decode +24% at 90k and +52% at 262k**, and **prefill +36-57%** (501 to 726 tok/s at 90k depth). The patch includes `GGML_V100_FA=vec|tile|mma` and `GGML_V100_UPSTREAM_BUILD=1` switches for A/B testing ([Mitsuasa513](https://raw.githubusercontent.com/Mitsuasa513/llama.cpp-v100-tuning/v100-sm70-tuning/README.md)). This targets the cluster's worst regime directly. Its gains overlap partly with tensor split, since both relieve KV reads, so the combined gain will be less than the product of the two. Nobody has published results with the patch combined with tensor split.

A third kernel source is the Volta port of 1Cat's FLASH_ATTN_V100 into a llama.cpp fork, reported in issue #28037. The report claims **no decode gain and up to 39.9% prefill** at unnamed contexts, and the repository could not be found ([issue #28037](https://github.com/ggml-org/llama.cpp/issues/28037)). It is worth watching but not worth acting on yet.

### Rank 3: retune quant, KV cache and draft length

IQ3_S is the smallest option but probably not the fastest per byte on Volta. IQ formats decode through codebook lookups, which cost loads on every matmul ([discussion #5617](https://github.com/ggml-org/llama.cpp/discussions/5617)). On a V100, ik_llama.cpp found that block-16 quants get worse MMQ than block-32 ones, and that one byte-gather fix moved an IQ4_K decode by 24% ([ik PR #2509](https://github.com/ikawrakow/ik_llama.cpp/pull/2509)). A V100-32GB llama-bench of the closely related Qwen3.6-27B gives Q4_K_M at 32.2 tok/s and Q8_0 at 22.8 ([ahelpme](https://ahelpme.com/ai/llamacpp-ai/llama-bench-the-qwen3-6-27b-and-nvidia-tesla-v100-sxm2-32gb/)). That works out to about 540 and 650 GB/s of effective bandwidth, against 900 nominal. Simpler dequantisation gets more out of the memory bus. No V100 measurement of IQ3_S exists, so whether Q4_0 or IQ4_XS beats it once tensor split frees memory has to be measured. Quality matters as well: the GSQ-RCO IQ3_S was presumably chosen for fit, and a 4-bit target is the higher-quality option if it is at least as fast.

Two smaller knobs follow. With the Volta kernel, f16 KV is about **5% faster** than q8_0 up to ~240k tokens ([Mitsuasa513](https://raw.githubusercontent.com/Mitsuasa513/llama.cpp-v100-tuning/v100-sm70-tuning/README.md)). The other is draft length. The V100 fork's accepted tokens per round fall from 3.23 at short context to 2.46 at 128K while round time rises ([llama.cpp-v100](https://github.com/1115714829/llama.cpp-v100)). Every rejected draft token still pays for attention over the full KV, so a shorter `--spec-draft-n-max` at depth is a plausible net win. Upstream MTP is not an option yet, because it does not support `-np > 1` ([unsloth](https://huggingface.co/unsloth/Qwen3.5-9B-MTP-GGUF)), and the cluster's DFlash2 acceptance is already above the fork's own.

## 1Cat-vLLM is the fastest V100 engine and cannot run here

The Volta ecosystem has consolidated around **1CatAI/1Cat-vLLM**. It has about 1.3k stars and released v1.5.1 on 2026-10-03. It ships a Volta-rebuilt FlashAttention reaching ~70 TFLOP/s causal attention, SM70 TurboMind W4A16 kernels, a GDN kernel, Qwen3.8-27B with the same `incoai/Qwen3.8-27B-DFlash2` drafter, and GGUF IQ3_S operators ([1Cat-vLLM](https://github.com/1CatAI/1Cat-vLLM)). On **4×V100-32GB at TP4** it reports single-request decode of **229 / 201 / 171 tok/s at 4K / 32K / 128K** and about 4,069 tok/s prefill at 32K. Its README warns that these figures come from different test "contracts" ([1Cat README](https://raw.githubusercontent.com/1CatAI/1Cat-vLLM/main/README.md)).

It is blocked on every platform axis. The wheel is x86_64-only and needs glibc ≥ 2.38, Python 3.12, PyTorch 2.10, the CUDA 12.8 toolkit for TileLang JIT, and driver ≥ 570 recommended ([1Cat README](https://raw.githubusercontent.com/1CatAI/1Cat-vLLM/main/README.md)). The node has glibc 2.17, a 12.4 CUDA ceiling and driver 550. The newest CUDA-enabled PyTorch for Power that the research found is Open-CE's 2.1.2 ([Open-CE 1.11.0](https://github.com/open-ce/open-ce/releases/tag/open-ce-v1.11.0)). IBM's current ppc64le torch wheels carry no CUDA tag and need glibc 2.34 ([IBM wheels](https://wheels.developerfirst.ibm.com/ppc64le/linux/torch/2.10.0+ppc64le1)). Porting it would mean building PyTorch 2.10, Triton and TileLang for ppc64le against CUDA 12.4 and then back-porting a CUDA 12.8 codebase. That is a research project, not an install.

The evidence for 2×16GB is also thin even on x86. The project calls TP2 a "bounded capability check". A dual-V100-16GB user hit OOM following its docs and went back to llama.cpp ([Juejin](https://juejin.cn/post/7655376386387984399)). A third-party 16GB V100 test without NVLink measured ~97 ms per output token for GPTQ-Int4 at TP2 under concurrency 4. The same test found that the Volta GDN kernel failed to JIT and that an older image lacked Qwen3.8 features in a way that "would have caused silent numerical errors" ([emmy PR #733](https://github.com/cloudrift-ai/emmy/pull/733)). Its best use here is as a **kernel donor**: its D256 split-D attention and decode-GEMV ideas are what a llama.cpp port would borrow.

The rest of the field is closed off. Upstream vLLM now requires compute capability 7.5 ([vLLM docs](https://docs.vllm.ai/en/latest/getting_started/installation/gpu/)), and its ppc64le support is CPU-only ([IBM blog](https://community.ibm.com/community/user/powerdeveloper/blogs/manjunath-kumatagi/2024/06/27/run-vllm-on-ppc64le-architecture)). The one public POWER9+V100 vLLM GPU attempt crashed and was never resolved ([IBM community](https://community.ibm.com/community/user/discussion/server-crashes-after-starting-vllm-and-ollama-power9)). SGLang needs sm_75 and now CUDA 13 ([SGLang docs](https://docs.sglang.io/get_started/install.html)). TensorRT-LLM does not list Volta ([support matrix](https://nvidia.github.io/TensorRT-LLM/reference/support-matrix.html)). LMDeploy still lists V100 but not Qwen3.8, and it needs PyTorch ([LMDeploy models](https://lmdeploy.readthedocs.io/en/latest/_sources/supported_models/supported_models.md)). ExLlamaV3 supports Qwen3.5-family architectures, but it is Ampere-tuned and PyTorch-bound ([exllamav3](https://github.com/turboderp-org/exllamav3)). ik_llama.cpp supports Qwen3.8 and DFlash, but it is officially Turing-or-newer, and its maintainer has declined to tune for Volta, calling it "wasted effort" without a dedicated maintainer ([ik #2463](https://github.com/ikawrakow/ik_llama.cpp/issues/2463)). qengine's +48% over llama.cpp on sm_70 comes with no NVLink support and broken DFlash ([DEV](https://dev.to/haru-neo/i-wrote-a-custom-cuda-inference-engine-to-run-qwen35-27b-on-130-mining-cards-732)).

## What to benchmark first, and in what order

**Step 0: measure today's baseline.** Run `llama-bench` without the drafter, at `-sm layer`, with depths 0, 16K, 64K and 100K and the same FA and KV settings as production. This replaces the inferred 25-40 tok/s raw decode with a real number and shows how much of each step is weights and how much is attention. Then run a fixed set of *real* code-agent prompts through `llama-server` with DFlash2 at those depths, both alone and with two concurrent requests. Use real prompts because the V100 fork shows synthetic prompts inflate speculative numbers. Every later step is compared against this run.

**Step 1: get an NCCL for ppc64le with CUDA 12.4.** First check whether spack, which already supplied the cluster's cuda-12.0 nvcc, can build one. If not, build NCCL from source against `/usr/local/cuda-12.4`. Run `nccl-tests` all_reduce on the two NVLink-connected GPUs with `NCCL_P2P_LEVEL=SYS` and confirm it uses P2P over NVLink. Small-message latency here also validates the allreduce estimate behind the TP ceiling.

**Step 2: two tensor-split builds, A/B.** Rebuild the current upstream commit with `GGML_CUDA_NCCL=ON` and `CMAKE_CUDA_ARCHITECTURES=70` using the 12.4 toolkit. Build 1115714829/llama.cpp-v100 v1.1.1 the same way. Run each with `--split-mode tensor --tensor-split 1,1`, FA on, explicit `--ctx-size 262144 -np 2`, the IQ3_S target and DFlash2, under `numactl --membind=0,8`, and repeat Step 0. Watch VRAM over a long session for the CUDA-graph leak. Record per-GPU memory, because balanced cards may allow a 4-bit target.

**Step 3: layer on Volta kernels.** Port or cherry-pick the Mitsuasa513 patch onto the winner of Step 2, and use `GGML_V100_FA` to A/B it at depth.

**Step 4: sweep the cheap knobs.** On the best build, compare IQ3_S, Q4_0 and IQ4_XS targets, f16 and q8_0 KV, and draft n-max of 7, 5 and 4 by depth band.

**Step 5: validate correctness at serving depths.** Qwen3.8-27B in llama.cpp produces instant EOS at scattered prompt lengths between ~96k and 243k. The problem reproduces on CUDA, CPU and ik_llama.cpp, vLLM passes at the same depths, and the issue has no maintainer reply ([issue #27756](https://github.com/ggml-org/llama.cpp/issues/27756)). The cluster's 131072-token slots fall inside that band. Probe it on each candidate build before promoting it, since a faster build that ends sessions silently is a regression.

These tests take a node away from users. The four slots are shared by up to three users, so run them on one node during a quiet window and leave the other serving. If the winning build changes per-slot context or slot count, the client repo's coupling applies: `limit.context` and `limit.input` in `config/opencode.json`, the model display names and the gateway's derived context must all follow `QWEN38_CTX / QWEN38_SLOTS`.

## Conclusion

Asking for a "V100-tailored engine" points at the wrong layer for this cluster. The Volta-specific work that matters in 2026 lives in kernels and parallelism strategies, not in a separate serving stack. The one stack that packages that work end to end, 1Cat-vLLM, is out of reach because CUDA on Power stopped at 12.4.1, and no amount of user-space effort changes that. What remains available is significant. Both GPUs on each node currently take turns, the attention kernels at depth are the ones upstream itself calls untuned for Volta, and a fork exists that was built for this exact machine and model. The biggest realistic gains are in long-context decode and prefill, which are the regimes deep agent sessions spend most of their time in. Short-context decode is already close to what the hardware can do with speculation.

The largest uncertainty is not speed but provenance. Each promising number here comes from a single author on different quants, card counts or memory sizes. A day spent on the Step 0 baseline and the NCCL build will settle more than any further reading. The pattern to watch over the longer term is upstream absorbing these Volta kernels, such as split-D FA from issue #28037. That is the only route by which the cluster's improvements stay maintained without carrying a private fork.
