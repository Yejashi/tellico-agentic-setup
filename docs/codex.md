# Codex against the Tellico models

`codex` keeps using whatever you already have -- your OpenAI login is
untouched. `codex-tellico` runs the same Codex against the local Qwen servers.
Switching is a matter of which command you type.

```bash
codex                        # OpenAI, exactly as before
codex-tellico                # local Qwen, this device's node
codex-tellico 1              # local Qwen, pinned to node 1
codex-tellico --think xhigh   # more reasoning for one session
codex -p tellico             # the same profile, without the wrapper
```

The profile lives at `~/.codex/tellico.config.toml` and is generated by
`install.sh`. Your own `~/.codex/config.toml` is never written to: `-p` layers
the profile on top of it, so the default model, reasoning effort and trusted
projects you already have keep working.

## Four things that had to be true

Getting Codex onto a llama.cpp server is not just a base URL, and each of
these was found by trying it:

**`wire_api` must be `"responses"`.** It is the only value Codex 0.153 accepts
-- `"chat"` is rejected outright. That looked fatal until it turned out
llama.cpp implements `/v1/responses`, so the two meet after all.

**Reasoning effort must be overridden.** Codex sends its configured effort
straight through to the chat template, which accepts only `low`, `medium` and
`xhigh`. The usual Codex default of `high` -- which this repository's own
`~/.codex/config.toml` sets -- fails with a Jinja exception. The profile pins
`medium`, and `--think` changes it.

**Codex must go through the gateway, not a model server.** Codex sends
`instructions` *and* a `developer` message in the same request. llama.cpp
turns each into a system message, and the Qwen template raises `System message
must be at the beginning` on the second one, so every request fails. The
gateway folds developer and system input items into `instructions`, leaving
one leading system message. That is why `codex-tellico` resolves a gateway URL
and refuses to run without one.

**The gateway needs its own key.** Gateway authentication is per user, so the
shared cluster key is not a credential for it. A device installed with
`--gateway` already holds the right key. On a tunnel-mode device, ask the
operator for one and store it:

```bash
printf '%s' "$KEY" > ~/.config/tellico-qwen/gateway-key
chmod 600 ~/.config/tellico-qwen/gateway-key
```

## What it does not do

There is no `off` for thinking: Codex always requests reasoning, and it has no
way to send `chat_template_kwargs`, which is how OpenCode turns it off. The
levels are `low`, `medium` and `xhigh`.

Codex is a single-agent tool, so none of the dual-node orchestration applies.
One session uses one node, which is why `codex-tellico` spreads devices across
the two servers the same way `opencode-tellico` does.

## Settings

| Variable | Meaning |
|---|---|
| `TELLICO_CODEX_BASE_URL` | Gateway base URL, overriding what the mode implies |
| `TELLICO_CODEX_KEY_FILE` | File holding the gateway API key |
| `TELLICO_CODEX_NODE` | Force node 0 or 1 instead of deriving it |
| `TELLICO_CODEX_PROFILE` | Profile name, default `tellico` |
| `TELLICO_THINK` | Default thinking level |
